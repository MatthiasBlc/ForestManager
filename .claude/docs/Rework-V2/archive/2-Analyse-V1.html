Ce que fait Forest Manager, et ce qui coince

Le code est mieux fait que tu ne le penses. Ce qui est mal pense, c'est le modele metier des recettes et des roles, et une interface assemblee page par page. La V2 doit corriger les concepts d'abord ; le reste suivra.

Verdict en quatre points

  • Qualite technique correcte : validation Zod partout, CSRF, helmet, rate limiting, sessions en base, admin isole avec 2FA, 1010 tests backend et 563 frontend.
  • Modele recettes incoherent : une recette communautaire existe en 2 a N copies synchronisees a moitie (contenu oui, tags et suppression non). Les variantes naissent toutes seules quand on refuse une proposition.
  • Gouvernance incomplete : un moderateur ne peut ni retirer une recette, ni retrograder, ni exclure un autre moderateur. Une recette dont l'auteur est parti devient intouchable.
  • Interface sans systeme : daisyUI brut, composants mobiles a part, pas de cache de donnees cote front, des classes de theme utilisees mais jamais definies.

1. Usages

A quoi sert l'application aujourd'hui

Des groupes prives (famille, amis, colocs) partagent leurs recettes. Chaque utilisateur a aussi un carnet personnel. Un module de planning de repas, avec generation automatique, est reserve aux communautes a qui l'admin l'a accorde.

Utilisateur

  • Carnet perso : recettes avec photo, portions ajustables, temps, ingredients normalises, etapes, tags
  • Import depuis une URL (JSON-LD, HelloFresh corrige)
  • Profil, notifications temps reel, preferences par categorie

Membre de communaute

  • Voir et ajouter des recettes, proposer une modification
  • Partager (forker) une recette vers une autre de ses communautes
  • Suggerer des tags, fil d'activite
  • Planning de repas si la feature est accordee

Moderateur

  • Inviter par username, exclure un membre, promouvoir
  • Valider les tags PENDING et les suggestions de tags
  • Creer et generer le planning, regler ses parametres

SuperAdmin

  • Tags, ingredients (validation des PENDING), unites
  • Communautes, features, recettes, changelog
  • Journal d'audit, dashboard
2. Fonctionnement

Comment c'est construit

Backend

  • Express + Prisma, 26 controllers, 15 services, schemas Zod
  • Deux systemes de session isoles en base (user 1 h glissante, admin 30 min)
  • Socket.IO pour notifications et activite, rooms par user et par communaute
  • MinIO en upload presigne, conversion WebP, jobs cron de nettoyage

Frontend

  • React 18 + Vite + Tailwind 3 + daisyUI 4 (themes coffee / winter)
  • Client fetch maison, hook useAsyncData (pas de cache partage)
  • Layout sidebar + barre d'onglets mobile, bottom sheets
  • Fichier network/api.ts de 739 lignes

Livraison

  • GitHub Actions : tests, build, push registry, deploy Portainer
  • Prod au push sur master, preprod sur une PR vers master
  • Images en :latest uniquement, seed de 1467 lignes a chaque deploy

Le cycle de vie d'une recette en V1

Chaque fleche pleine cree une nouvelle ligne Recipe. Seules les fleches marquees "sync" se resynchronisent a l'edition, et seulement pour titre, temps, portions, image, etapes et ingredients.

3. Points non logiques ou douteux

Ce qui ne tient pas

Chaque point cite le fichier qui le montre. Les deux failles de securite sont reelles et exploitables par un utilisateur connecte ; elles meritent un correctif en V1 sans attendre la V2 (question Q16).

Critique

N'importe quel utilisateur peut ecouter l'activite d'une communaute

Securite
Preuve
backend/src/services/socketServer.ts:106 : socket.on("join:community", id => socket.join(...)) sans verifier l'appartenance.
Impact
Avec l'UUID d'une communaute, un user connecte recoit ses evenements d'activite en temps reel.
Proposition
Verifier la membership avant join. Correctif de quelques lignes.
Critique

L'import par URL contourne sa propre protection SSRF

Securite
Preuve
recipeImportService.ts:428 verifie le nom d'hote, puis :444 appelle fetch avec redirect: "follow".
Impact
Une URL publique qui redirige vers http://minio:9000 ou une IP interne passe le controle. Un nom DNS qui pointe vers une IP privee aussi.
Proposition
Redirections manuelles, resolution DNS et controle d'IP a chaque saut.
Critique

Une recette communautaire existe en plusieurs exemplaires synchronises a moitie

Modele metier
Preuve
communityRecipeService.ts:47 cree une recette perso et une copie ; recipeService.ts:303 resynchronise contenu, etapes et ingredients mais ni les tags ni la suppression (recipes.ts deleteRecipe ne touche qu'une ligne).
Impact
L'utilisateur voit sa recette en double, ne sait pas laquelle il modifie, et une suppression laisse des copies vivantes. Les forks et variantes divergent sans retour possible.
Proposition
Une recette, un espace d'origine, des partages par reference, une copie seulement sur demande (D03).
Important

Refuser une proposition fabrique une variante

Modele metier
Preuve
proposalService.ts:277 rejectProposal cree une recette isVariant au nom du proposeur. orphanHandling.ts fait de meme pour toutes les propositions en attente quand l'auteur quitte.
Impact
La liste des recettes se remplit de variantes que personne n'a demandees ; refuser n'est plus un geste neutre.
Proposition
Refuser ne cree rien ; le suggereur peut convertir sa suggestion en copie (D04).
Important

Une recette dont l'auteur est parti devient intouchable

Gouvernance
Preuve
Seul le createur edite ou supprime (membershipService.ts:57) et tranche une proposition (proposals.ts:354). La creation de proposition ne verifie pas que l'auteur est encore membre (proposals.ts:97).
Impact
Recette figee pour toujours, propositions qui restent en attente sans personne pour les traiter.
Proposition
Les moderateurs reprennent la main sur le contenu d'un ancien membre (Q02).
Important

Les moderateurs ne moderent pas le contenu

Gouvernance
Preuve
Aucune route ne permet a un moderateur de retirer la recette d'un membre ; seul l'admin plateforme le peut (admin/routes/recipesRoutes.ts). Pas de retrogradation, interdiction d'exclure un moderateur (members.ts:251), pas de suppression de communaute hors "dernier qui part".
Impact
Un groupe ne peut pas faire le menage chez lui ; un moderateur malveillant ne peut pas etre retire.
Proposition
Roles OWNER / MODERATOR / MEMBER avec une matrice claire (D06).
Important

La moderation bloque l'utilisateur en attendant quelqu'un d'autre

UX
Preuve
Tags d'espace crees PENDING, suggestions de tags a deux niveaux (PENDING_OWNER puis PENDING_MODERATOR), ingredients PENDING jusqu'a l'admin plateforme.
Impact
Beaucoup de code (tagService, tagSuggestions, communityTags : environ 1 200 lignes) pour un geste qui devrait etre immediat ; l'admin plateforme devient un goulot.
Proposition
Creation libre, nettoyage a posteriori (D08, D09).
Important

Le "perso" et le "communautaire" sont deux mondes

Modele metier
Preuve
Perso = communityId: null. Deux jeux de routes (/recipes, /communities/:id/recipes), deux regles d'acces, des interdits croises documentes (pas de proposition en perso, pas de share en perso, pas de publish en communautaire).
Impact
Le planning n'existe pas pour un utilisateur seul ; chaque nouveau module devra gerer les deux cas.
Proposition
L'espace perso est un espace comme un autre (D02).
Important

Les modules ne sont pas modulaires

Architecture
Preuve
Feature / CommunityFeature n'est accorde que par le SuperAdmin ; un seul module gate (requireFeature("MEAL_PLAN")) ; routes, nav et pages cablees en dur cote front.
Impact
Ajouter la liste de courses ou une liste de films touchera tout le code.
Proposition
Registre de modules, activation par l'OWNER de l'espace (D10).
Important

La prod a 68 commits de retard et le deploy n'a pas de retour arriere

Infra
Preuve
master = c100859 (2026-03-17). Images poussees en :latest seulement (deploy.yml). Preprod deployee uniquement sur une PR.
Impact
Impossible de savoir quelle version tourne, ni de revenir a la precedente. Changelog, planning et generation ne sont pas en prod.
Proposition
Tags par version et SHA, preprod au push sur la branche de travail.
Important

Pas de reinitialisation de mot de passe, deconnexion apres une heure

Comptes
Preuve
Aucun envoi d'email dans le projet ; session user maxAge 1 h glissante (config/session.ts:13) ; pas de suppression de compte.
Impact
Un mot de passe oublie = un compte perdu. Sur mobile on se reconnecte a chaque usage. Pas de conformite RGPD sur la suppression.
Proposition
Email (Q05), "rester connecte" (D13), suppression et export de compte.
Mineur

Recherche d'utilisateurs ouverte a tous

Securite
Preuve
GET /api/users/search renvoie les usernames par prefixe a tout user connecte.
Impact
Enumeration des comptes de la plateforme.
Proposition
Invitation par lien ou par username exact (D07).
Mineur

Code et schema morts

Dette
Preuve
Enum Visibility a une seule valeur ; RecipeView jamais ecrit, RecipeAnalytics seulement incremente au fork ; Notification.type en string libre.
Impact
Du schema a maintenir et a migrer sans usage.
Proposition
Retirer, ou typer (enum par module).
Mineur

Theme incomplet et interface sans systeme

Front
Preuve
border-forest-accent utilise dans routes/adminRoutes.tsx mais defini nulle part (le spinner admin est invisible) ; 272 btn daisyUI ecrits a la main ; composants mobiles separes ; body { overflow: hidden } avec scroll gere par conteneur.
Impact
Chaque ecran est un cas particulier ; personnaliser le theme demande de toucher tout le code.
Proposition
Design system shadcn/ui avec tokens (D16).
Mineur

La documentation a derive du code

Docs
Preuve
RECIPE_FLOWS.md annonce "editer : owner/membre", le code dit owner seul. Le README pointait vers docs/mvp/ supprime et citait Axios retire. CLAUDE.md listait des dossiers deplaces dans V1/.
Impact
On re-derive ce qui existe a chaque session.
Proposition
Fait dans ce chantier : docs rassemblees dans .claude/docs/, V1 archivee, regle "pas de recopie du code".
4. A garder

Ce qui est bon et qu'on recupere

Securite et socle

  • Validation Zod, CSRF double submit, helmet, rate limiting, limite de body
  • Admin isole : session dediee, TOTP, audit log
  • Codes erreur centralises

Fonctionnel

  • Import JSON-LD et ses correctifs
  • Algorithme de generation du planning (regles, poids, frequences, cooldowns)
  • Ingredients normalises et unites categorisees
  • Notifications persistantes et groupees

Outillage

  • Tests d'integration API sur vraie base
  • Upload presigne MinIO + nettoyage
  • Changelog genere par la CI

6. Design system

Une interface unique, modulaire, personnalisable

shadcn/ui (Radix + Tailwind v4) : les composants sont copies dans le depot, donc on les possede et on les modifie. Tout passe par des tokens CSS ; chaque espace porte sa propre couleur d'accent, appliquee quand on y entre. Une seule interface pour desktop et mobile.

7. Evoluer ou reecrire

Trois options

A - Faire evoluer

Refactor feature par feature

Pour : pas de big bang, prod toujours a jour.

Contre : chaque etape doit rester compatible avec le modele de copies que l'on veut supprimer ; le front daisyUI serait refait ecran par ecran en cohabitant avec l'ancien. Le plus long au total.

C - Recommandee

Front reecrit, back refondu par module

Meme depot, monorepo avec package partage. On reprend infra, securite, admin, import, generation et tests ; on remodele les recettes, les espaces et les roles ; une migration de donnees unique, repetee sur une copie de la prod.

Contre : V1 gelee pendant le chantier (sauf correctifs).

B - Tout reecrire

Nouveau depot from scratch

Pour : page blanche.

Contre : on jette du code qui marche (auth, admin, securite, import, algorithme), on refait l'infra, et la migration reste necessaire de toute facon.
